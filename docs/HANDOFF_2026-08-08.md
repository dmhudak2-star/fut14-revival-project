## What changed today, and it is real

**The FUT login runs its whole server-side bootstrap.** In one second:

```text
POST /ut/auth -> GET phishing/trusteddevice -> GET settings
              -> PUT match/reset -> GET user -> GET userdata
```

No `phishing/question`, no `phishing/validate`, no unanswered request, no 404.

Three changes got it there:

1. **Removed the probe at `0x8910AAF8`.** It sat on the tail every
   notification id shares -- walked constantly, not once per login. Six cycles
   before it reached `LoginToFUT`; the four after it did not. Do not
   reinstate a hook on that address.
2. **Trusted device answers `{"trusted":true,"changed":false,"exists":true,"locked":false}`**,
   as the PC reference does. This removes the security question at protocol
   level, which also removes the account-state drift that used to suppress
   `/ut/auth` entirely.
3. **`accountinfo` serves an empty persona list**, as the PC reference does.
   A populated persona claims a FUT account whose club, squad and identity
   this server cannot then produce.

Also added `/ut/game/fifa14/squad/1`; route coverage against the reference is
now 36/36.

## Two conclusions from the old handoff are wrong

**`FirstTimeInit` is not a login step.** `0x8909FC40` registers ION viewmodels
by name (`futloginviewmodel`, `futsecuritycheckpointviewmodel`,
`futgamehubviewmodel`, `futNewUser`, ...). It returns 1 because that is all it
was ever going to do. Its success and its notification are not a login
completion, and reading them as one was reading the name rather than the code.

**`GetIdentityData` is not the judge of this stall.** `fcc_login1` puts it on
the returning-user path, which serving an empty persona list deliberately
closes. Its staying at zero agrees with the intent. The popup is the judge.

## Where the stall actually is

`fcc_login.big` decodes, and settles the first state completely:

```text
BeginLogin()        popup {message:"Loading", nButtons:0}; setInterval(Check_AdapterInit)
Check_AdapterInit() polls ION_FCC.LoginToFUT
Handle_LoginToFUT() -> Login()
Login()             setFlowState(FUT_GAME_MODE), OSDKCards_Init,
                    SetGameMode(FUT2), FirstTimeInit, ACTION_ADVANCE
```

That is the live trace exactly, so **`futLogIn0` completes** and the flow
legitimately sits on `fcc_login1`. The stall is inside `fcc_login1`, at
`CardsLoginHelper.Init(..., OnError, InitialLoginDone)` / `DoInitialLoginSteps`.
`OnError` does not fire either, so the callback pair is not invoked at all.

Native side, for orientation: `LoginToFUT` (`0x89105D18`) is an adapter over
the singleton at `*0x892213A0` = `0xB5A9F018`, vtable `0x89008E90`,
implementation `vtable[1]` = `0x8908D350`, which binds to the script symbol
`_global.LoginToFUT`. The full `ION_FCC` API name table is at `0x89016DD0`.
`CardsLoginHelper` and `DoInitialLoginSteps` are in neither the table nor
`0x89000000..0x89030000`.

## Open, with the traps marked

* `data/ui/game/globalclasses/classloader.big` (in `data0.big`, offset
  `0x31D9C0`, `0x10738` bytes) still does not decode. **The bit-offset sweep
  result is a false positive**: offsets 4, 34 and 43 decode 236000 bytes
  without raising, and produce noise -- no `BIGF` magic, 71.6% zeros against
  33.3% for a real decode. Check `BIGF` before claiming a decode.
* 97 of 169 `ion_fut` script entries fail to decode, so any negative result
  from scanning them is not exhaustive.
* The PC reference had to patch its nav to add the `iceBreaker` route, which
  this build already declares. Worth re-reading what that implies about how
  the reference gets past this same screen.

## Constraints that still hold

Do not force `EnterFUT2`, `login-success`, `GameSceneEnable`, `FutCreateClub`
or an ION screen. Do not reset the FUT loader `+0x114`. Do not neutralise the
`this+0x48` counter. Do not launch the server from a shell that exits. Screen
captures and heap scans while the title is playing cause severe stutter; the
title is idle on the popup now, so reads there are safe.
