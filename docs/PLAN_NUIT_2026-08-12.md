# Plan de nuit — 12 août 2026

Objectif : qu'un joueur puisse **faire dans FUT tout ce qu'un joueur fait dans
FUT**, et que je le vérifie moi-même, sans personne devant la console.

La contrainte qui décide de tout le reste : je n'ai pas d'yeux. Le framebuffer
n'est pas fiable sur cette console, la capture d'écran XBDM l'est encore moins.
Ce que j'ai à la place est meilleur que je ne le croyais — **le journal du
serveur est un oracle d'écran**. Chaque écran de FUT a une signature de
requêtes qui n'appartient qu'à lui : le hub demande `clientdata/totw` puis
`clubUser`, la boutique demande `storepackdescriptions`, une coupe demande
`tournament/teams` puis `tournament/user/<id>`. Si je sais quelles requêtes
arrivent, je sais où je suis. Et `tools/xbox360_virtual_input.py` me donne la
manette.

Manette + journal = boucle fermée. C'est là-dessus que repose toute la nuit.

## Phase 0 — ne rien casser (fait avant d'écrire ce plan)

Une chose devait être réglée avant de lancer quoi que ce soit en autonomie, et
elle l'a été : **la suite de tests écrasait la vraie sauvegarde du club.**

`tests/test_fifa14_blaze_server.py` importe le module serveur ; l'importer
construit un club vivant à partir de `runtime/club-save.json`, et toute route
testée qui sauvegarde écrivait *ce fichier-là*, avec ce que le test venait de
faire aux globales. C'est ce qui a mangé la coupe en cours : entrée à 00:33,
disparue du fichier à 00:38:27, réécrite avec une table de tournois vide par un
`pytest` lancé entre les deux. Rien ne prévenait ; le fichier revenait
simplement plus petit.

`SAVE_FILE` lit maintenant `FIFA14_CLUB_SAVE`, et `tests/conftest.py` le pointe
sur un fichier temporaire avant tout import. Vérifié : 350 tests passent et le
vrai fichier ne bouge pas d'un octet.

C'est la condition pour que je puisse tester toute la nuit. Sans ça, chaque
`pytest` de la nuit aurait grignoté son club.

Reste à ajouter :

- un instantané horodaté du club avant **chaque** expérience, pas seulement
  avant les grosses
- un club bac à sable (`FIFA14_CLUB_SAVE=runtime/club-save.bac-a-sable.json`)
  pour tout ce qui touche à l'économie, pour que rien de ce que je fais cette
  nuit n'apparaisse dans son solde demain matin

## Phase 1 — le pilote automatique

`tools/fut_drive.py` :

1. **presse** des touches via le pad virtuel
2. **attend** une signature de requêtes dans le journal, avec un délai
3. **dit** où il pense être, ou qu'il est perdu
4. **détecte le gel** — plus rien dans le journal + `xbeinfo running` qui
   répond encore = frontend gelé ; XBDM muet = titre mort
5. **récupère seul** : magicboot, attente du dashboard, `tools/fut.sh`,
   reprise du scénario là où il en était

Le point 5 est ce qui transforme « je teste » en « je teste toute la nuit ».
Deux gels ce soir ont coûté chacun un aller-retour avec un humain.

Un scénario est une liste de couples (touches, signature attendue). Le premier
que j'écris est le seul qui compte pour l'instant : dashboard → menu principal
→ Ultimate Team → coupe → **jouer un match** → écran de récompense.

## Phase 2 — pourquoi le titre gèle sur une coupe

Deux gels ce soir, tous les deux sur `GET /ut/game/fifa14/tournament/user/3`,
et le second sur une réponse **identique octet pour octet** à ce que le client
avait lui-même envoyé en PUT. Le document n'est donc pas en cause.

Mitigation en place : une coupe entrée mais jamais jouée (round 1, blob de
progression vide) n'est plus annoncée comme reprenable. On ne perd rien — aucun
match n'a été joué — et le tirage est refait à l'entrée.

Mais ça ne dit toujours pas *pourquoi*. L'hypothèse à tester en premier n'est
pas HTTP du tout : **le client attend peut-être une trame Blaze qu'on ne lui
envoie jamais**. Reprendre une coupe, c'est reprendre une partie ; dans Blaze,
une partie appartient au GameManager (composant 4). Le gel sans aucune requête
qui suit ressemble beaucoup plus à un `waitForNotification` qui n'arrive jamais
qu'à un parseur JSON qui se noie.

D'où la phase suivante.

## Phase 3 — recherche : Zamboni et la pile Blaze

Zamboni est une réimplémentation libre des serveurs Blaze d'EA pour les NHL
360/PS3 — même génération, même pile, souvent les mêmes numéros de composants.
Ce que je vais y chercher, dans l'ordre :

- **GameManager (composant 4)** : `createGame`, `joinGame`,
  `advanceGameState`, `finalizeGameCreation`, et surtout les **notifications
  asynchrones** — `NotifyGameSetup`, `NotifyGameStateChange`,
  `NotifyPlayerJoining`. Les identifiants de notification et la disposition
  des TDF sont ce qui manque ici.
- **GameReporting (composant 28)** : commande 2 et la notification 114 de
  résultat. Le revival PC les utilise déjà ; Zamboni donne la forme côté
  serveur pour de vrai.
- **Matchmaking** : `startMatchmaking` / `NotifyMatchmakingFinished`. Même
  hors ligne, le client passe souvent par là pour une partie contre l'IA.
- **UserSessions / Association lists** : ce que le client exige avant
  d'accepter d'entrer en partie.

Sortie : `docs/BLAZE_GAME_MANAGER.md`, avec pour chaque trame la source et ce
qui reste supposé. La règle du projet ne change pas : **rien ne part sur le fil
qui ne soit pas vérifié dans le binaire ou observé sur le fil.**

## Phase 4 — tout ce qu'un joueur doit pouvoir faire

Inventaire complet, avec l'état réel. C'est la liste que la nuit doit faire
descendre.

### Jouer — la priorité absolue

| | état |
|---|---|
| jouer un match de coupe de bout en bout | **gèle** |
| écran de récompense après match | calculé côté serveur, jamais affiché |
| progression de coupe | codé, jamais vu tourner |
| saisons | servies vides — **trou complet** |
| matchs contre l'équipe de la semaine | `/match` et `/match/ready` renvoient `{}` |
| amicaux | non exploré |

### Le club

| | état |
|---|---|
| voir les joueurs | ✅ |
| voir les consommables, par catégorie | ✅ (réglé ce soir) |
| appliquer un consommable | codé, **jamais déclenché depuis la console** |
| vendre rapidement | ✅ |
| objets de club (maillots, écussons, ballons, stades) | servis, jamais assignés |
| nommer le club, choisir écusson et maillot | **nom codé en dur** |

### Les transferts

| | état |
|---|---|
| chercher sur le marché | implémenté, **jamais exercé en jeu** |
| enchérir / acheter maintenant | implémenté, non vérifié |
| liste de transferts, objets non assignés | partiel |
| liste de surveillance, mes enchères | non fait |

### La boutique

| | état |
|---|---|
| acheter un pack avec des coins | ✅ |
| contenu et cotes des packs | ✅ mesuré |

### L'équipe

| | état |
|---|---|
| voir l'équipe, changer la formation | partiel |
| échanger deux joueurs | non vérifié |
| chimie | non calculée |
| plusieurs équipes | stockées |

L'ordre de la nuit suit ce qu'un joueur touche le plus : **jouer un match**
d'abord, et tout ce qui en découle (récompenses, coupes, saisons). Un FUT où
l'on ne peut pas jouer n'est pas un FUT, quelle que soit la qualité du marché.

## Phase 5 — le TU3 statique

À faire pendant une fenêtre où je ne pilote pas le jeu : les fichiers du TU
sont verrouillés (`414- access denied`) dès que FIFA tourne.

1. tirer les deux paquets, l'original et le `.codex-patched` déjà présent
2. `stfs_extract.py` sur chacun, sortir `patch.big` / `patch.bh`
3. contrôle décisif : la taille de l'enregistrement 2218 dans `patch.bh` — si
   elle vaut encore 17 942, le `.codex-patched` ne contient rien
4. régénérer proprement si besoin, réinjecter, revérifier l'arbre SHA-1
5. sauvegarder l'original **sur le Mac**, pas seulement à côté sur la console

Gain : plus de surveillance du patch, plus de course avec le titre qui recharge
`helperFunctions`, plus de « le patch n'est pas passé ».

## Ce que je ne ferai pas cette nuit

- Toucher au club réel pour une expérience. Bac à sable pour tout.
- Envoyer sur le fil un membre dont je n'ai pas trouvé le nom dans le binaire.
  Construire à l'aveugle a déjà figé ce titre plusieurs fois.
- Installer un TU patché sans avoir vérifié l'enregistrement 2218 et sauvegardé
  l'original sur le Mac.
- Laisser la console dans un état inutilisable au réveil.
