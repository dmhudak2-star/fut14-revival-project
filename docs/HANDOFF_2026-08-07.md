## What was learned today

**The account state was gating `/ut/auth`.** After the security question was
answered at 13:02, this server persisted `OPTQ`/`OPTS` and `FirstTimeFlag`,
and the client never authenticated again in any later session — which quietly
invalidated every measurement taken after that point. Clearing
`user_settings` and `account` in `runtime/local-account.json` brings the whole
login sequence back. Anything that reads "no `/ut/auth`" should check this
first.

**The notification is delivered, and handled.** Operation `0xDF`, which
`FirstTimeInit` submits, reaches the engine notification bus at `0x8278F228`
and is dispatched to a live listener at `0xB5C56308`. Resolving that listener
gives its vtable `0x890175C8` and handler `0x8910A798`, inside CardsDLL. That
handler is a switch on the notification id, and `0xDF` has its own case at
`0x8910A9EC`, which calls `0x8909DD90` and `0x8909FC40`.

So the earlier "no listener registered" and "the notification is dropped"
readings were both wrong. The chain runs; it stops somewhere inside those two
functions.

`0x8909FC40` sets a flag byte at `+0xC`, then loads `cards/ini/fcc.ini` and
the FUT view models (`futonlineseasonsviewmodel`,
`futofflineseasonsviewmodel`, `futauctionsearchviewmodel`) and touches
`fifa_ng_db`. `cards/ini/fcc.ini` is in neither `cards0.big` nor `data1.big`,
and there is no `cards\` directory on the console. Whether that path is on the
live route or only in an error branch is **not established**.

**CardHouse is never opened.** Component 2148 appears in no journal. The
client uses 30722 for its session and never issues a CardHouse command,
although this server's own notes call that session mandatory.

## Measured after that was written

`0x8909FC40` **is entered** — once, in the same cycle that records
`LoginToFUT` and `FirstTimeInit`, and still with `GetIdentityData` never
called. It is now part of the traced set as `FirstTimeInitNotify`.

So the whole path runs: `FirstTimeInit` submits `0xDF`, the bus dispatches it,
CardsDLL's handler switches to the `0xDF` case, and that case's function
executes. The stall is inside that function or immediately after it, not
anywhere upstream.

Disassembling it shows a five-fold repeating shape — build a string through
`0x8909fbd0`, call through a resolved pointer, test the result, call
`0x89051950` — over the FUT view-model names in rdata
(`futonlineseasonsviewmodel`, `futofflineseasonsviewmodel`,
`futauctionsearchviewmodel`, ...), alongside `cards/ini/fcc.ini` and
`fifa_ng_db`. It is loading the FUT view models.

## It returns

The exit probe answers it:

```text
FirstTimeInitNotify   1 call     entry, 0x8909FC40
FirstTimeInitReturn   1 call     epilogue, 0x890A06D0
GetIdentityData       never called
```

The function runs to completion. So the view-model loop is not where the
bootstrap stops, and `cards/ini/fcc.ini` is not implicated — it is reached on
an error branch or not at all.

Everything from `FirstTimeInit` to the end of its notification handler now has
a measurement saying it ran. The stall is strictly downstream of
`0x8909FC40` returning.

## What I would do next

Follow the handler's tail. After calling `0x8909FC40` the `0xDF` case stores
zero at `0x70(r1)`, calls `0x890662E8`, and joins the common exit at
`0x8910AAE8`. That common tail is shared by every notification id the handler
knows, so it is where a result is published back — and `fcc_login1` is waiting
on exactly such a publication (`CardsLoginHelper`'s `InitialLoginDone`).

The tail is short and worth reading before instrumenting anything:

```text
0x8910AAE8  li r5, 0
0x8910AAEC  bl 0x8910A6A0        publish a named value
0x8910AAF0  cmplwi cr6, r28, 0
0x8910AAF4  beq cr6, 0x8910AB0C  nothing to notify
0x8910AAF8  lwz r11, 0(r28)      otherwise call r28's vtable+4
0x8910AB08  bctrl
```

`r28` comes from `0x50(r1)`, built at entry by `0x8908CA10`. So the tail
publishes, then notifies an interface if one is bound.

`0x8910A6A0` turns out to publish one fixed key, and reading it settles what
the value means:

```text
0x890175AC  "FE::FIFA::GameSceneEnable"
```

So the `0xDF` case publishes `GameSceneEnable = 0` — hide the 3D scene, which
is exactly right when the FUT interface takes over, and the neighbouring cases
publishing `1` are the ones that restore it. It is not a status, and the
asymmetry I flagged here first is not evidence of failure. Discount it.

That leaves the tail doing its job: it publishes the scene state and then
notifies the bound interface. Where the chain actually loses the thread is
between that and anything calling `GetIdentityData`.

`CardsLoginHelper` is native, and that is now settled rather than assumed.
Decoding every entry under 300 KB in `cards0.big`, plus the class and
framework entries in `data1.big` and all 164 entries of the TU archive
`data0.big`, finds `DoInitialLoginSteps` and `InitialLoginDone` in exactly one
place: `fcc_login1` itself, where they are the names it calls and waits on.
The class implementing them is in `CardsDLLzf.xex.dll`, which is XEX2 on disk
and only readable from console memory.

`GetIdentityData` is an operation the client asks for, not one the engine
pushes. `fcc_login1` hands its sequence to `CardsLoginHelper.DoInitialLoginSteps`
and waits for `InitialLoginDone`; that script is what would ask for it after
`FirstTimeInit` reports back. So the missing link is the completion being
reported to the ActionScript side, and the ION action-pipeline and
provider-publication traces already in this repository are the instruments for
it — `--trace-ion-action-pipeline`, `--trace-provider-publication` on
`fifa14_early_local_server.py`.

Do not spend another pass on the archive patches until that is understood.
Three of four runs with the route patch go strictly less far than retail, and
the favourable one ended in a connection error.

## Where this leaves it

Three independent measurements now agree on the same boundary:

* the native chain runs to the end of its notification handler and returns;
* the provider boundary publishes the screen and then goes quiet;
* the action pipeline never fires at all.

So `CardsDLL` finishes handling `FirstTimeInit`'s notification and never
reports a result to the script side. `fcc_login1` is waiting on exactly that
report, and it is the only step in the sequence with no measurement showing it
happen.

The next instrument is a hook on whatever CardsDLL uses to call into
ActionScript — not the provider boundary, which is the engine's own, but
CardsDLL's own callback path into `gCardsLoginHelper`. Finding it means
locating, in CardsDLL, the code that would invoke `InitialLoginDone`, and the
handler tail at `0x8910AAE8` is the place it would be called from.


## Where CardsLoginHelper is, and what is not yet ruled out

`CardsLoginHelper` is the class `fcc_login1` hands its login sequence to, and
it is the only step with no measurement showing it run. Searching for it:

* **Not in CardsDLL.** Scanning the mapped image for `CardsLoginHelper`,
  `DoInitialLoginSteps`, `InitialLoginDone` and `gCardsLoginHelper` finds
  none of them, so the native side does not call back by name — the script
  passes function references to `Init` and native calls them by handle.
* **Not in any archive that decodes.** Every entry under 300 KB of
  `cards0.big`, the class and framework entries of `data1.big`, and the 110
  decodable entries of the TU archive `data0.big` contain the name in exactly
  one place: `fcc_login1`, which references it. No archive has a `classes/`
  directory at all — checked across `data1`, `data2`, `data3`, `data5`,
  `data6`, `data7`, `datax` and `cards0`.

**The limitation, stated plainly:** 54 of `data0.big`'s 164 entries do not
decode with this repository's decoder, and the large-resource form defeats
libmspack too at every window size. `globalclasses/classloader.big` is one of
them — 236,000 bytes uncompressed, and the obvious place for a class registry.
So "nowhere" is not exhaustive, and the classloader is the specific gap.

Resources whose uncompressed size exceeds 64 KiB do not use the
`FF <u16><u16>` frame header — the sizes will not fit — and the decoder now
handles that shape, but their bitstream needs something further.

**They are multi-chunk.** The container's chunk count is 2 for
`fifa_ng_db-meta.xml`, not 1, and that is the actual difference — not the
frame header. The single-chunk layout puts one `(stored, block type)` pair at
offset 40 and the payload at 48; a resource with two chunks carries more, and
its entry is larger than its stated `stored` size by exactly the amount the
second chunk needs. None of the descriptor layouts tried gives a plausible
stored size for that second chunk, so where the payload begins is still
unknown. The decoder now refuses these outright instead of decoding from the
wrong offset.

What is known about the large form, from `globalclasses/classloader.big`
(236,000 bytes uncompressed, 67,336 stored):

* the LZX bitstream does **not** start at the payload offset; skipping twelve
  bytes is what libmspack will accept at all;
* from there it produces exactly 65,536 bytes and then fails, at every reset
  interval and window size tried;
* **and that output is noise** — no strings, no structure. So the twelve-byte
  skip is not the answer either, it merely gets far enough to produce
  something. Do not build on it.

What the two forms look like side by side, from the TU archive's 123 short
and 24 long resources:

```text
short (total <= 0xFFFF)   ff 06d0 015c ...   marker, raw u16, packed u16
                          ff 05f7 028e ...   and both match the header exactly

long  (total >  0xFFFF)   12ce3320 492a954d 00500700 ...   setplays.big
                          16601920 0b4ead4e 00600000 ...   attribdb.vlt
                          305e1320 89c7b54d 00400000 ...   attribdb.bin
                          3b0a0220 79be910c 00c64300 ...   fifa_ng_db.db
                          349a1e20 67e67114 00400400 ...   a font
```

The fourth byte of the first word is `0x20` in every long resource sampled but
one, where it is `0x10`. That is a field, not noise, and it is the thread to
pull: the long form is a different framing rather than the short one shifted.

The large form is therefore still unidentified, and with it the only place a
class registry could hide.
