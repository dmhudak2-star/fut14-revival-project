## What was learned today

**The account state was gating `/ut/auth`.** After the security question was
answered at 13:02, this server persisted `OPTQ`/`OPTS` and `FirstTimeFlag`,
and the client never authenticated again in any later session — which quietly
invalidated every measurement taken after that point. Clearing
`user_settings` and `account` in `runtime/local-account.json` brings the whole
login sequence back. Anything that reads "no `/ut/auth`" should check this
first.

**The notification is delivered, and handled.** Operation `0xDF`, which
`FirstTimeInit` submits, reaches the engine notification bus at `0x8278F228`
and is dispatched to a live listener at `0xB5C56308`. Resolving that listener
gives its vtable `0x890175C8` and handler `0x8910A798`, inside CardsDLL. That
handler is a switch on the notification id, and `0xDF` has its own case at
`0x8910A9EC`, which calls `0x8909DD90` and `0x8909FC40`.

So the earlier "no listener registered" and "the notification is dropped"
readings were both wrong. The chain runs; it stops somewhere inside those two
functions.

`0x8909FC40` sets a flag byte at `+0xC`, then loads `cards/ini/fcc.ini` and
the FUT view models (`futonlineseasonsviewmodel`,
`futofflineseasonsviewmodel`, `futauctionsearchviewmodel`) and touches
`fifa_ng_db`. `cards/ini/fcc.ini` is in neither `cards0.big` nor `data1.big`,
and there is no `cards\` directory on the console. Whether that path is on the
live route or only in an error branch is **not established**.

**CardHouse is never opened.** Component 2148 appears in no journal. The
client uses 30722 for its session and never issues a CardHouse command,
although this server's own notes call that session mandatory.

## The two archive patches, measured

Both are transposed from the PC revival project, byte-identical edits where
the data is byte-identical, and both are built in place: same file length,
same slot, one byte of the directory record changed, contents re-encoded and
verified against libmspack.

* **Icebreaker route** (`futLogIn1 / advance` → `iceBreaker`). One run out of

* **`fcc_login1` popup** (`EQUALS2` → `OR`). Removes the popup, and stops the

Neither is active. Both are one rename away on the console.

## Tooling added today

* `tools/archive/lzx_decode.py`, `tools/archive/lzx_encode.py` — read and
  write the archives' LZX resources. Validated against libmspack as an outside
  judge: it decodes retail streams and ours to identical bytes at a 128 KiB
  window. The encoder fits a patched resource back into its own slot, which is
  required — a relocated resource boots the title to a black screen.
* `tools/xbdm_transfer.py` — `getfile` frames its body with a four-byte
  little-endian length. Reading past it is not optional: every archive this
  project had pulled off the console was shifted by four bytes, which is what
  froze the title four times and sent me chasing the compression and the
  bytecode edit, both innocent. `verify` reads an upload back and compares.
* `tools/notify.sh` — mail for a milestone or a blocker.
* `docs/navgraphs/` — the decoded FUT navigation graphs.

## Measured after that was written

`0x8909FC40` **is entered** — once, in the same cycle that records
`LoginToFUT` and `FirstTimeInit`, and still with `GetIdentityData` never
called. It is now part of the traced set as `FirstTimeInitNotify`.

So the whole path runs: `FirstTimeInit` submits `0xDF`, the bus dispatches it,
CardsDLL's handler switches to the `0xDF` case, and that case's function
executes. The stall is inside that function or immediately after it, not
anywhere upstream.

Disassembling it shows a five-fold repeating shape — build a string through
`0x8909fbd0`, call through a resolved pointer, test the result, call
`0x89051950` — over the FUT view-model names in rdata
(`futonlineseasonsviewmodel`, `futofflineseasonsviewmodel`,
`futauctionsearchviewmodel`, ...), alongside `cards/ini/fcc.ini` and
`fifa_ng_db`. It is loading the FUT view models.

## It returns

The exit probe answers it:

```text
FirstTimeInitNotify   1 call     entry, 0x8909FC40
FirstTimeInitReturn   1 call     epilogue, 0x890A06D0
GetIdentityData       never called
```

The function runs to completion. So the view-model loop is not where the
bootstrap stops, and `cards/ini/fcc.ini` is not implicated — it is reached on
an error branch or not at all.

Everything from `FirstTimeInit` to the end of its notification handler now has
a measurement saying it ran. The stall is strictly downstream of
`0x8909FC40` returning.

## What I would do next

Follow the handler's tail. After calling `0x8909FC40` the `0xDF` case stores
zero at `0x70(r1)`, calls `0x890662E8`, and joins the common exit at
`0x8910AAE8`. That common tail is shared by every notification id the handler
knows, so it is where a result is published back — and `fcc_login1` is waiting
on exactly such a publication (`CardsLoginHelper`'s `InitialLoginDone`).

Trace `0x8910AAE8` and whatever it dispatches into. If the tail publishes,
the loss is on the ActionScript side and the ION action pipeline traces in
this repository apply. If it does not, the `0xDF` case reaches it in a state
the tail rejects, and the zero stored at `0x70(r1)` is the first thing to
read.

Do not spend another pass on the archive patches until that is understood.
Three of four runs with the route patch go strictly less far than retail, and
the favourable one ended in a connection error.
